---

## 0. 直接回答

| 问题 | 答案 |
|---|---|
| **① 生图能提速吗** | **能，3 路并行 → 46.7min 压到 ~15.6min（3×）**。但有个**前置条件必须先做**：当前 API 无法把任务钉到指定渠道，不改的话三路会退化成单路打同一个渠道，提速拿不到（详见 §2.1） |

## 2. 改善方案

### 2.1 生图三路并行（46.7min → ~15.6min）

**收益**：`2801s / 3 ≈ 934s ≈ 15.6min`，**3×**

**⚠️ 必须先拆的拦路石（否则三路=白做）**

渠道选择写死在 `_call_with_failover` 内部，且**每次都从全局最优渠道开始**：

```python
# services/image.py:57-61
channels = self.relay.all()
channels.sort(key=lambda c: health[c.name].score(), reverse=True)  # 全局最优排第一
for ch in channels[:self.max_attempts]:                             # 无脑从最优开始
```

`generate()` **没有指定渠道的入参**，`RelayManager` 只有 `pick()`（返回唯一最优）和 `all()`。
→ 3 个 worker 并发调用会**全部打到同一个 score 最高的渠道**，三路退化成单路三倍压力，直接把该 key 打 429。

**实施步骤**

1. `generate(req, channel: Channel | None = None)` —— 传入则跳过排序、只打该渠道；不传 = 保持原 failover 语义（不破坏现有调用）
2. `RelayManager` 加 `claim()` / 内部锁（`record`/`_save` 加 `threading.Lock`，**注意文件是 `app/managers/relay.py` 不是 `services/`**）
3. 新增 `generate_many(jobs) -> {id: path}`：
   - worker 数 = `min(渠道数, 任务数)`，每 worker 领一个渠道
   - 幂等：`out_path` 已存在且 >50KB 则跳过
   - 失败：**指数退避 + jitter** 后换到另一个渠道的队列（不做退避会打成重试风暴）
   - 全渠道失败才 raise，已成功文件保留
4. `config.image.primary.concurrency` 语义改为「每渠道并发」，**默认锁 1**（先别开 3×2=6，会把中转 QPS 打满）

**验收**：56 张墙钟 ≤ 1100s，且三个渠道**都被用到**（用 mock 断言三渠道均有调用）

---

### 2.2 生图 ∥ TTS 并行（14.5min → 折进生图窗口内）

**为什么能并行**：生图 = subrouter.ai（3 个 key），TTS = 阿里云百炼 DashScope，**两家独立厂商、独立配额、独立限流**。现在做不到纯粹是因为 `produce` 固定 `script → tts → compose`，**压根没有 image stage**。

**关于 cosyvoice3.5**：已经是默认引擎，不用换——
```python
# voice.py:35
ENGINE_DASHSCOPE = "cosyvoice"   # 主用：阿里云百炼 CosyVoice v3.5-flash
DEFAULT_ENGINE = ENGINE_DASHSCOPE
```

**实施步骤**

1. 新增 `stage_images`：读 `episodes/{id}/image_prompts.json`（laogongtuan 已有现成文件），走 `generate_many`
2. 新增 `stage_assets`：`ThreadPoolExecutor(2)` 同时跑 `stage_tts` 与 `stage_images`
3. **TTS 自身也并行**（额外省 ~10min）：`voice.synthesize` 现在是 `for f in frames` 串行；改 `ThreadPoolExecutor(4~6)`，按 DashScope 限流调（**先测 4，看 429 再调**）
4. `produce` 顺序改为 `script → assets → shots → compose → verify`
5. `save(ep)` 在两侧**都结束后写一次**，避免半写入

**收益**：`max(15.6, 4) ≈ 15.6min`（原 46.7+14.5 = 61min）→ **资产阶段 61min → 16min，3.9×**

### 2.3 渲染分段 + 断点续跑（失败域 21min → 90s）

**现状为什么必须从头**：单条 ffmpeg 管道从第一帧写到最后一帧，中途断 = `.tmp` 缺 moov = 整个不可用（本次实测：崩在 423MB，删掉重来）。没有任何检查点。

**实施步骤**

1. 抽出 `_encode_video_span(timeline_slice, upscaled, out_mp4)`（只出视频，不混音）
2. 按 `compose.segment_max_sec`（默认 90）在**镜头边界**切段
3. **`@2x` 超分必须在切段之前全片一次性构建**，作为只读入参传给各段
   （现在有 `_up_cache` 按底图去重，60 张只超分一次；若写进段内会退化成 14 段 × 60 张重复放大）
4. 段编码**去掉 `-movflags +faststart`**（它会在段末做一次重写抬内存——正是本次 pagefile 崩溃的同类风险点），只在最终 mux 加
5. 段视频 `concat demuxer -c copy` → 一次 mux 全片音轨 → 原子改名为 `{id}_m1.mp4`

**⚠️ 段完成判据必须修对，否则续跑失效**

段跳过条件是 `nb_frames == expected`。但注意两种口径不等：

```
A) round(段总时长/1000*25)      ← compose 现有的 expected
B) Σ 逐镜 round(单镜/1000*25)   ← plan_frames 实际写出（= 成片真值）

实测 laogongtuan（90s 切 15 段）：11 段 A≠B（差 1~5 帧）
全片：A=31461  B=31487（差 26 帧）
```

**若用 A 判据，73% 的段永远判不完 → 每次仍全量重编，分段白做。**

修法——统一真值函数，全片/分段/断言共用：

```python
def _expected_frames(timeline_slice) -> int:
    """段预期帧数 = Σ 逐镜帧数。必须与 plan_frames 的 round(dur_s*fps) 同口径。"""
    return sum(max(1, round(sh.duration_ms / 1000.0 * FPS)) for sh, *_ in timeline_slice)
```

> 这个 26 帧差一直没暴露，是因为现有 `expected` 只用于 `n_total < expected` 的断管检测（`>=` 就放行）；改成分段的**等值判据**后才成为硬伤。

6. `expected_frames < segment_min_frames`（默认 2500 ≈ 100s）走旧单段路径，保证已交付短片行为不变
7. mux 前断言 `|视频总时长 − 音频时长| < 250ms`（现在刻意不用 `-shortest`，不能靠它兜底）

**收益**：总编码时间不变（~44min，体积/时长决定），但**失败域 21min → 90s**，且已完段真跳过。

## 3. 收益汇总

| 阶段 | 现状 | 优化后 | 倍数 |
|---|---|---|---|
| 生图 56 张 | 46.7 min | ~15.6 min（3 路） | **3×** |
| TTS 365 帧 | 14.5 min | ~4 min（4 路） | **3.6×** |
| 生图 + TTS（并行取 max） | 61 min | **~16 min** | **3.9×** |
| 渲染 21min 片 | ~44 min | ~44 min（分段） | 1× |
| **全流程** | **~105 min** | **~60 min** | **1.75×** |
| **渲染失败代价** | **44 min 从头** | **90 s 一段** | **29×** |

> 渲染总量省不下来（体积 = 时长 × cq，与分段无关）。分段的价值是**把不可运维的 21 分钟单次赌博，变成 14 个可续跑的 90 秒任务**。

## 4. 落地顺序（按依赖，先做前置条件）

```
① 半天  帧数真值函数 _expected_frames + 测试      ← 不做这个，分段续跑是假的
② 1天   渠道钉住(channel=) + generate_many 三路   ← 生图提速的前置条件
③ 1天   分段 compose（超分段前构建 / 段去 faststart）
④ 半天  stage_assets 并行（生图 ∥ TTS）+ TTS 自身并发
⑤ 半天  锁 / 退避 / QPS 闸 / mux 时长断言
⑥ 回归  重跑分段路径，成片须 = 31487 帧，与现有 766MB 单管道成片一致
```

**验收硬指标**（防止"看起来做完了"）

- 生图：56 张墙钟 ≤ 1100s，**且三渠道均被调用**
- TTS：365 帧 ≤ 5 min
- 分段：中断后重跑，**15 段全部命中跳过**（不是重编）
- 成片帧数 = 31487，与现有成片一致
- 现有 14 例测试 + 新增用例全绿
