## 1. 会自动花掉多少钱

`episodes/xlc-01/` 下**没有** `scene_plan.json` 和 `image_prompts.json`，所以 `prepare()` 走 else 分支：**159 个 unit → 159 个 ImageJob → 159 次付费调用**，每张 1080×1920 / quality=low，且 `requires_upscale=True`（还要再 2× 放大）。

对照既有集的人工分镜：

| 集 | plates | scene 数 | frames | plates/frame |
|---|---|---|---|---|
| caomin-02 | 46 | 46 | 295 | 0.156 |
| caomin-03 | 47 | 47 | 301 | 0.156 |
| caomin-04 | 39 | 39 | 244 | 0.160 |
| laogongtuan | 56 | 69 | 365 | 0.153 |
| lishimin-01 | 78 | 78 | 220 | **0.355** |
| lishimin-02 | 64 | 64 | 197 | 0.325 |
| lishimin-03 | 59 | 100 | 287 | 0.206 |
| lsm-15min | 64 | 64 | 324 | 0.198 |

按 caomin 系列的密度，xlc-01 需要 **约 25 张**。自动起草是它的 **6.4 倍**。

你此前明确说过："底图不能增加太多，那样太慢，成本太高。" 159 张直接撞在这条上。

## 2. 更严重的问题：自动 prompt 的质量不可用

`prepare()` 的兜底分支把**旁白原文**当画面主体：

```
Historical documentary scene illustrating the following narration.
No written text, captions or watermark. Narration: <unit 原文>
<style_suffix> <negative_clause>
```

实测 159 个 unit 的旁白长度：**min=7 / p25=22 / median=31 / p75=46 / max=112 字**。

其中 **31 个 unit 整句不足 20 字，且是对话、引文或设问**，例如：

- `narr-83f2ea92fa177ec9` → `"朕佳儿佳妇，今以付卿。"`（帝王遗言）
- `narr-8d6e88f5cfa79ecb` → `长孙无忌是怎么回答的？`（设问）
- `narr-a3abaadfe2dc8f0b` → `"宗社事重，法不可赦。"`（台词）
- `narr-b45000bcd5c7323f` → `太宗留下了生平最后一句话：`（无画面）

把这些喂给生图模型，得到的是**与剧情无关的图**。而且 `prepare()` 自己给这批产物打了 `review_required: True`——仓库自己都不认为它们能直接用。

**所以 159 张的真实构成是：约 25 张可用的画面 + 134 张为凑数而存在的填充。** 这不是省钱与费钱的区别，是那 134 张无论花多少钱都不会产生可用素材。

## 3. 根因：粒度，不是图量

159 个 unit 来自 Gemini TTS 专版的 8 段安全分块格式，每段内又是独立短段落，`prepare` 按段切单元。而 v2 是"一句一镜"，于是 159 unit → 159 shot。

caomin 系列是 47 unit / 295 帧，一镜约 6.3 秒；xlc-01 是 159 unit / 159 帧，一镜约 8.3 秒但画面主体只在其中几句。**shot 切得比画面变化更碎**，图片自然要跟着切碎。

这不是图片阶段的 bug，是**上游切分粒度与画面切换粒度不匹配**。

## 4. 三个选项

| | 做法 | 付费次数 | 可用性 |
|---|---|---|---|
| **A** | 直接跑 images | **159** | 约 25 可用 + 134 张噪声 |
| **B** | 先写 `scene_plan.json` + `image_prompts.json`，合并同场景的 unit 到一张 plate | **约 25** | 按既有集水准 |
| **C** | 先只跑 images 的**预检**（`screen_image_prompts` / job 构建），不调 API | **0** | 只得到计划，看清哪些 unit 无画面可画 |

我的建议是 **B**，理由：它同时解决成本（6.4×）和可用性（31 张垃圾图），而且与全部 14 集既有做法一致——`build_image_jobs()` 读的就是这两个文件，`screen_prompt()` 会先体检每张 plate。

但 **B 需要你的创作输入**：哪些 unit 共用一张 plate、每张 plate 的主体是什么。这我可以先做 C 拿到候选清单，再按你的判断合并，不用你从零写。

如果你说"A 就跑"，我会跑，但会把 25/134 这个账和 `review_required` 一起留在产物里。

## 5. 我现在不敢替你决定的另一件事

xlc-01 的 159 个 unit 意味着**如果直接出片，会有 159 个 shot**。既有集是 195–365 帧 / 195–365 shot。159 shot 本身不算异常，但它和 25 张 plate 搭配时，**每张 plate 要被复用约 6.4 次**——这正是你之前说"同一底图约连续 23 秒、吸引力不够"的那个问题。

所以 C 之后可能还需要谈 shot 合并（`_continuity_breaks` 那条链），那是构图决策，不是编码决策。
