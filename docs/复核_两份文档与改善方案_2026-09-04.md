## 2. 方案文档缺陷（按严重度）

### 🔴 B-1【致命】段完成判据用错口径 → 断点续跑失效

方案原文：

> 3. 每段：`build/segments/seg-XXX.mp4`；若已存在且 `nb_frames == expected` 则跳过

**问题**：compose 现有的 `expected` 口径是 `round(段总时长/1000*25)`（一次舍入），
而 ffmpeg 实际写出的帧数 = `Σ 逐镜 round(单镜时长/1000*25)`（逐镜舍入）。
两者**不相等**，逐镜舍入会累积。

**实测（laogongtuan 真实数据，90s 切段）**：

```
全片：round(1258444ms/1000*25) = 31461   ← compose 现有 expected 口径
       Σ 逐镜 round(d/1000*25)  = 31487   ← plan_frames 实际写出（= 成片真值）
       差 26 帧

按 90s 切成 15 段，逐段比对：
  段1  A=2187 B=2189 ✗    段2  A=2220 B=2225 ✗    段3  A=2205 B=2205 ✓
  段4  A=2174 B=2173 ✗    段5  A=2242 B=2247 ✗    段6  A=2181 B=2183 ✗  ...
  → 15 段中 11 段 A≠B（差 1~5 帧）
```

**后果**：73% 的段永远判不成「已完成」，每次重跑都全量重编。付了分段重构的全部代价，拿不到「中断后续跑」这个**唯一的核心收益**。

**修法**（三行，且顺带修掉另一个隐患）：

```python
# compose.py 内建单一真值函数，全片/分段/断言共用
def _expected_frames(timeline_slice) -> int:
    """段预期帧数 = Σ 逐镜帧数。必须与 plan_frames 逐镜舍入同口径。"""
    return sum(max(1, round(sh.duration_ms / 1000.0 * FPS)) for sh, *_ in timeline_slice)
```

- 段判据改用 `_expected_frames(slice)`
- `timing_assert._shot_frames` 与 `plan_frames` 的 `round(dur_s*fps)` 本已同式，把 #5 也切到这个函数 → 顺带消掉我上一轮修的「31461 vs 31487」口径差
- 现在 `expected` 只用于 `n_total < expected` 的断管检测（`>=` 即放行），所以这个 26 帧差一直没暴露；改成分段后它就成了硬伤

### 🔴 B-2【致命】「每渠道钉 1 个 worker」当前 API 做不到

方案原文：

> worker 数 = `min(渠道数, 任务数)`，默认每渠道 1 路

**问题**：渠道选择写死在 `_call_with_failover` 内部，且**每次都从全局最优开始**：

```python
# services/image.py:57-61
channels = self.relay.all()
health   = {c.name: self.relay.health(c.name) for c in channels}
channels.sort(key=lambda c: health[c.name].score(), reverse=True)   # ← 全局最优排第一
for ch in channels[:self.max_attempts]:                              # ← 无脑从最优开始
```

`ImageGenerator.generate(req)` **没有任何指定渠道的入参**；`RelayManager` 只有 `pick()`（返回唯一最优）和 `all()`（返回全部）。

**后果**：3 个 worker 并发调用 → 三者都拿到同一个 score 最高的渠道 → 三路并行**退化成单路三倍压力**，直接把该 key 打 429，再触发三路同时换路。**方案的核心收益（≈1/3 墙钟）同样拿不到。**

**修法**：

1. 给 `generate()` / `_call_with_failover()` 加 `channel: Channel | None = None`；传入即跳过排序、只打该渠道（失败向上抛，由 `generate_many` 决定换路）
2. 或给 `RelayManager` 加 `claim()` / `lease()`，worker 启动时各领一个渠道
3. `generate_many` 内按渠道建 worker，任务失败 → 换到**另一个 worker 的渠道**队列

配套：方案说「单张 `generate()` 保持原 failover 语义，不破坏现有调用」——加可选 `channel` 参数即可同时满足（不传 = 原逻辑）。

### 🟠 B-3【高】relay 文件路径写错 + 确认无锁

- 方案写 `app/services/relay.py` → **实际是 `app/managers/relay.py`**
- 核验 `RelayManager.__init__ / _save / record` **确实全无锁**（`pick()` 也无）
- 3 线程并发 `record()` → 健康度 lost update；并发 `_save()` → tmp 写竞争

**修法**：锁加在 `RelayManager` **内部**（`self._lock = threading.Lock()`，`record`/`_save`/`pick` 全部 `with self._lock`），不要靠调用方加锁——否则方案文档说的「`record`/`_save` 加锁」会被实现成各 worker 各加各的锁，等于没加。
`_save` 现在的 `tmp.replace()` 原子写是对的，保留。

### 🟠 B-4【高】分段后 `@2x` 超分会被重复执行

现状有个重要优化（方案未提及）：

```python
# compose.py:366-370  场景复用下多 shot 共用一张底图，超分只做一次
_up_cache: dict[str, Path] = {}
upscaled = {}
for sh, _, _ in timeline:
    if sh.image_path not in _up_cache:
        _up_cache[sh.image_path] = upscale(sh.image_path)
    upscaled[sh.id] = _up_cache[sh.image_path]
```

若按方案的 `_encode_video_span(timeline_slice, upscaled, ...)` 签名，实现者极易把超分写进段内 → 缓存作用域退化为段内 → **14 段 × 60 张重复超分**，把省下的编码时间赔进去。

**修法**：明确 `upscaled` 必须在**切段之前全片一次性构建**，作为只读入参传入各段。在方案里写死这条约束。

### 🟡 B-5【中】并行缺退避 → 429 重试风暴

方案：「某路 429/失败则该任务回队列换路」。三路同时 429 时会无间隔狂转，且把中转 QPS 拉高三倍（方案自己也在风险里提到「三路并行会把中转 QPS 拉高」）。

**修法**：失败换路前 `sleep(指数退避 + jitter)`；加全局 QPS 闸（如令牌桶，默认 ≤ 2 QPS/渠道）；单任务换路上限 = `n_channels`，超了才 raise。

---

### 🟡 B-6【中】`stage_images` 数据源存在循环依赖

方案：「读 `episodes/{id}/image_prompts.json`（或 shots 里缺文件的 prompt）」。

- 实测只有 `episodes/laogongtuan/image_prompts.json` 存在（该集特供），新集没有
- 「shots 里缺文件的 prompt」这条**循环依赖**：`shots` 在 `assets` 之后才生成，而 `assets` 又要读 shots

**修法**：把 `image_prompts.json` 定为**唯一入口**（约定 schema：`[{image_id, prompt}, ...]`）；无该文件时 `stage_images` **skip 并明确告警**，不要静默产出「0 张图」然后让 `shots` 阶段因缺图失败。laogongtuan 现有文件即现成样板。

---

### 🟡 B-7【中】音画对齐缺少验收断言

流程变成「段视频 concat → 一次 mux 全片音轨」后，若段边界/舍入使视频总长与 `narration.wav` 差几十 ms，长片会累积成可见漂移。现有代码刻意**不用** `-shortest`（注释说会提前截断），所以不能靠它兜底。

**修法**：mux 前断言 `abs(视频总时长 - 音频时长) * 1000 < 250ms`，超了就 raise 而不是静默出片。

---

### 🟢 B-8【低】段编码不应加 `+faststart`

`+faststart` 会在段末做一次 moov 前移重写，**抬内存**——正是本次 compose 首次崩溃（WinError 1455 pagefile）的同类风险点。中间段根本不需要流式优化。

**修法**：段编码去掉 `-movflags +faststart`，只在**最终 mux** 那一步加。

## 4. 改善方案（按优先级给出落地顺序）
