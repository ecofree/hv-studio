## 二、硬阻断

### 1. lishimin-01 卡在分镜之前（唯一的生产目标）

```
episodes/lishimin-01/  →  audio/（空）  script.md
frames=220   shots=0   audio wav=0   图片=0   段=0   成片=无    status=scripted
```

`episode shots` 是**声明式装配**，只读 `episodes/{id}/scene_plan.json`（`app/cli.py:98`），  
而仓内**没有任何自动生成分镜的工具**：

```bash
grep -rn "def .*scene_plan|auto.*plan|build_plan" app/ bin/   # 无结果
```

历史集的分镜都是一次性脚本产出的（`bin/hanwu_ch3_shots.py`、`bin/m2_shots.py` …）。  
也就是说 220 帧的分镜 + 生图提示词是**纯内容工作量**，代码帮不上忙。

对比：laogongtuan / lsm-15min 都有 `scene_plan.json` + `image_prompts.json`，  
唯独 lishimin-01 两样都没有。

## 三、代码缺陷（真 bug）

### 3. `hv relay sync` 必崩：`TypeError: Object of type datetime is not JSON serializable`

复现：

```bash
python -m app.cli relay sync
#   File "app/managers/relay.py", line 210, in _save_locked
#     tmp.write_text(json.dumps(data, ...))
# TypeError: Object of type datetime is not JSON serializable
```

根因链：

| 位置                          | 内容                                                                         |
| --------------------------- | -------------------------------------------------------------------------- |
| `app/models/relay.py:119`   | `QuotaSnapshot.fetched_at: datetime = Field(default_factory=datetime.now)` |
| `app/managers/relay.py:92`  | `to_dict()` 用 **`model_dump()`** —— 保留 datetime 对象，不转字符串                   |
| `app/managers/relay.py:210` | `json.dumps(data)` → 炸                                                     |

（`model_dump_json()` 才会序列化，`model_dump()` 不会。）

**影响面（三个调用点）**：

| 调用点                                                 | 是否包裹             | 后果                  |
| --------------------------------------------------- | ---------------- | ------------------- |
| `app/cli.py:132` `hv relay sync`                    | 否                | 直接崩，报错退出            |
| `app/controllers/v1/video.py:21` `POST /relay/sync` | **否**            | 该接口 500             |
| `app/main.py:19` FastAPI lifespan                   | 是（try/except 吞掉） | 启动不崩，但**静默失败**，更难发现 |

**最实际的后果**：`sync_quota()` 是唯一刷新 `last_quota` 的路径。它一崩，  
`score()` 里的配额惩罚 `-500`（`relay.py:66`）**永不生效** ——  
渠道没钱的时候调度器不会降权，只能靠一次次失败慢慢学。

**唯一的好消息**：崩在 `json.dumps`，早于 `write_text`，  
所以 `state/relay_health.json` 没被写坏（仍是 9/5 的完整文件，已验证尾部完整）。

**不阻塞生图主链路**：`app/services/image.py` 不调用 `sync_quota`。

## 五、环境风险

### 4. compose 会随机崩（本次审计跑了 7 遍，结果来回横跳）

| 次数           | 结果                             |
| ------------ | ------------------------------ |
| 清理前          | **204 passed**                 |
| 清理后 ×3       | 3 failed → 2 failed → 2 failed |
| 单独跑 compose  | 2 failed                       |
| 还原现场后再跑      | 2 failed（证明与清理无关）              |
| **本次审计最后一次** | **204 passed**（89s）            |

失败时的错误：

```
[h264_nvenc @ ...] CreateInputBuffer failed: out of memory (10)
[vf#0:0 @ ...] Error sending frames to consumers: Cannot allocate memory
x264 [error]: malloc of size 11744448 failed
[WinError 1455] 页面文件太小，无法完成操作
```

**不是显存不足**：`nvidia-smi` → `83MiB / 12288MiB`，几乎全空。  
真因是 **NVENC 会话/固定内存分配受系统内存压力影响**，而：

- **页面文件只配了 2048MB**（32GB 内存的机器，当前已用 162MB / 峰值 197MB）  
  —— `app/services/compose.py` 自己的注释就写着  
  「低 pagefile 机器上首次 compose 崩 WinError 1455」的同类风险
- `nvidia-smi` 显示 `GameViewer.exe`（**C+G**）挂在 GPU 上，可能占着 NVENC 会话

同一份代码能 204 全过也能 202 通过 —— **这是抖动，不是坏代码**。  
但它意味着真出片时**有可能渲染到一半挂掉**。

### 5. TTS 逐帧默认 + 并发无开关

- 默认档位已退回逐帧（`6caf64b`）→ lishimin-01 = **220 次独立请求**
- `synthesize(workers=4)`（`voice.py:228`）但 **`orchestrator.stage_tts` 从不传 workers**，  
  且 **CLI 没有 `--workers` 参数** → 永远 4 路并发，无法下调
  ```bash
  grep -n "workers" app/cli.py   # 无结果
  ```
- 重试只有 2 次（`_TTS_TRANSIENT_RETRY`，可经 `HV_TTS_TRANSIENT_RETRY` 调），  
  退避 0.5s / 1s（`voice.py:152`）—— 扛不住持续限流
- 实测教训：D 档 83 次突发撞 `Throttling.RateQuota`，只成功 25 帧，降到 `workers=2` 才补完

- Windows 回收站 `D:\$RECYCLE.BIN\S-1-12-1-...` 今天有活动

**内容本身零损失**（这点是确定的）：

- `lsm-regress` 成片与 `lsm-15min` 成片 **md5 一致**（`e14e2d34d2a1f4e704ee433a432754f5`），纯副本

- `resync-1540` 是 2048 字节的假 mp4

**但"移进 `.trash_hv` 后又被别的东西清掉"这件事必须查清楚** ——  
全仓只有 `bin/hanwu_ch3_repair_frames.py:49` 会往 `.trash_hv` 写，  
没有任何代码删它（已 grep 确认）。若真有外部自动清理在跑，
