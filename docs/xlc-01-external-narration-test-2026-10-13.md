## 1. 素材核验

| 项 | 值 |
|---|---|
| 音轨 | 24000 Hz / mono / 16-bit PCM / 31,978,560 采样 / **1332.44s（22.21 min）** / 61.0 MiB |

**24 kHz mono 正是 `narration_pipeline.wave_info` 唯一接受的格式**，所以母带进链不需要任何重采样。这印证了当初把 `SAMPLE_RATE` 设为 24000 与外部母带对齐是对的。

## 2. 两个必须先解决的格式缺口

### 2.1 `setup_episode_from_writing_dna.py` 无法解析新剧本

发布版工具的幕标头正则是 `^###\s*【第.幕[：:]`。新 writing-DNA 成稿格式写作：

```
### 【第一幕 (A段)：翠微宫遗诏与帝王隐忍】（字数：943 字）
```

`幕` 与 `：` 之间有 `(A段)`，**正则完全不匹配**，工具会以"找不到 `### 【第…幕` 幕标头；这不是 writing-DNA 成稿格式"退出。后果是**新格式的剧本无法建档**，只能手工清洗。

**最小修复**：把正则放宽为 `^###\s*【第.幕[^】\n]{0,14}[：:]`，容许括号分块标签。这是唯一改动，其余规则不变。

### 2.2 `strip_script_markdown` 不剥代码围栏（更严重）

Gemini TTS 专版把口播正文包在围栏里：

````
```text
贞观二十三年五月，终南山翠微宫的阴雨，笼罩了整个大唐帝国。
```
````

`strip_script_markdown` 没有处理 ``` ，于是**围栏标记本身变成了口播文本**进入 v2 unit。未修复时实测：

```
unit[0].source_text = "```text贞观二十三年五月，终南山翠微宫的阴雨，笼罩了整个大唐帝国。"
unit[158]末尾      = "……露出了它致命的獠牙。```"
```

后果：159 个 unit 里 **2 个 unit 的文本含 ``` 字面量**，ASR 不可能"听出"这三个反引号，`asr_check` 必然报 insertion/submission。这是**字面门禁与字幕完整性**问题，且**没有任何门禁会响**（帧文本确实等于清洗后的剧本）。

**最小修复**：`strip_script_markdown` 增补围栏行剥离。本次实测我已从 narration 源手工移除 16 行围栏。

### 2.3 `[pause=0.5s]` 被正确丢弃

新剧本的 4 处 `[pause=0.5s]` 不在 `KEEP_BRACKET` 白名单（`重音|停顿[\d.]*秒`）内，被正确移除。这是对的——它是 TTS 指令不是口播词，音轨里的停顿由母带自带。

## 3. v2 切分结果

script stage 产出 **159 个 unit / 5707 口播字**。

| | caomin-02（旧格式） | xlc-01（新格式） |
|---|---|---|
| unit 数 | 47 | **159**（3.4×） |
| 口播字数 | 4882 | 5707 |
| 字/unit | 104 | 36 |

粒度差 3.4 倍的原因：新格式是 Gemini 的 8 段安全分块，每段内又是独立短段落，`narration_pipeline.prepare` 按段落切单元。**这不是缺陷**（更细的单元 = 更准的对齐），但直接影响下游成本：v2 是"一句一镜"，所以 **shot 数也会是 3.4 倍**，`_encode_v2_segment` 的段数、运镜连续性校验量同比上升。做新集时必须预估这一点。

围栏修复后：0 个 unit 残留 ``` 或分块元数据，`（字数：943 字）` 也未泄漏。

## 5. 关键发现：`MIN_UNIT_COVERAGE` 硬门禁误杀正确切片

159 个 unit 中唯一低于 0.6 的是 index 3：

```
narr-83f2ea92fa177ec9
  text : "朕佳儿佳妇，今以付卿。"
  cov  : 0.385   (chars=13, hits=5)
  span : 27.56s - 29.02s
```

这是**文言引文**。自由 ASR 听成：

```
want  : 朕佳儿佳妇今以付卿
heard : 朕家而家負       (CER 88.9%)
```

（`佳儿佳妇`→`家兒家父`，`今以付卿` 完全丢失；且 ASR 输出为繁体，与我在审计中发现的 16/47 繁化现象同源。）

但它的区间 27.56–29.02s **干净地夹在**两个正确对齐的邻段之间（前段 24.12–26.30 覆盖率 0.923，后段 31.30–37.68 覆盖率 0.906）。

### 用权威判据裁决

`MIN_UNIT_COVERAGE` 只是**启发式预筛**。真正的切分权威是下游 `forced_alignment`：它是**强制对齐器**，拿源文本去音频里找每个词的位置，不做自由听写。我用与 `build()` 完全相同的路径裁出该 unit 并裁决：

```
cut span 27.26s .. 29.32s = 2.06s
FA.align OK: 13 words
  first 6 words: ['"', '朕', '佳', '儿', '佳', '妇']     ← 源文本词元，不是听写结果
FA.atoms OK: 13 rows
```

**结论：切片是正确的。** 强制对齐器按源文本找回了 `朕/佳/儿/佳/妇` 全部词元，`atoms()` 通过 13 行（13 字文本 ↔ 13 行）。也就是说 `MIN_UNIT_COVERAGE=0.60` 把"ASR 听不懂文言"误判成"切片切错了"，**拒绝了一个正确的切片，直接让整个 build 失败**。

```
ExternalNarrationError: 1/159 个 unit 的对齐覆盖率低于 60%：narr-83f2ea92fa177ec9=38%
```

### 这是我自己的设计缺陷

`dc1ab07` 里我把覆盖率设成硬门禁，理由是"覆盖率低意味着边界不可信"。实测证明这个理由**区分不了两种成因**：

| 成因 | 覆盖率 | 切片 | asr_check | atoms |
|---|---|---|---|---|
| 切到邻段 | 低 | **错** | failed | **failed** |
| ASR 听不懂原文 | 低 | **对** | failed | **passed** |

两种的 asr_check 都是 failed，差别只在 atoms。而 atoms 是下游一定会跑的、更强的判据。

**正确设计**：覆盖率应该是**逐 unit 的可审查标记**（`alignment_review`），不是 build 级硬失败；`start is None`（真的无法定位）才必须是硬失败，因为那种情况下连切都切不了。这与 `asr_check` 失败 20/47 却仍能产出 manifest、只让 `technical_quality: pending` 的处理完全同构。

**最小修复**：`_check_alignment` 把低覆盖率从 raise 改为返回 `low_coverage_units` 列表，写入 manifest 与 `alignment[i].coverage`（已有该字段）；`validate_external` 对低覆盖率 unit 校验 atoms 证据而非再次用阈值卡住；发布门禁要求这些 unit 有人工处置，与 `production_quality.pending()` 同一条路。

⚠️ **这需要改生产代码，按你此前的要求我没有动。** 本次实测是用内存里改 `MIN_UNIT_COVERAGE=0.0` 跑通的，仓库 `external_narration.py` 仍是 0.60。
