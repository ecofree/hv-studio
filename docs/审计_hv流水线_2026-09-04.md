## 1. P0 高危（静默产出错误，无报错）

> 三条均已人工复核到源码，非子代理单方面结论。共同特征：**不在本次出片路径上被触发，但一旦边界条件命中就静默产出错的成片，且 ffmpeg 仍 rc=0**。

### 1.1 TTS 幂等只认"文件存在"，不认"文本是否变了" — `app/services/voice.py:157,164`
```python
if f.audio_path and Path(f.audio_path).exists():
    continue  # 幂等
...
if wav.exists():            # 只查文件在不在
    f.audio_path = str(wav)...; continue
```
`Frame.id` 无内容指纹（`episode.py:75` 只有 `"frame-001"`），`narration_text` 变了但旧 wav 还在 → **静默复用旧音频**。
- **本次审计中就复现过**：合并句子后重跑 TTS，`frame-000` 因 wav 已存在而复用 1560ms 旧音频（须手动删 wav 才重合成）。这是真实发生过的 P0。
- **风险触发场景**：改旁白/多音字词典/换音色后重跑，不删旧 audio 目录 → 全片部分镜头配旧音。无任何告警。

### 1.2 upscale 复用无"源图变更"失效检测 — `app/services/upscale.py:56-62`
```python
if dst_p.exists():
    ... if _d.size == (sw*2, sh*2): return dst_p   # 只看尺寸，无 src mtime/hash
```
只校验 `@2x` 尺寸是源图 2 倍，**不校验源图是否被重新生成过**。重跑 `m2_scenes.py` / `hanwu_new_scenes.py` 生成新底图后，旧 `@2x` 因尺寸仍匹配而被静默复用 → **画面内容过期但无报错**。
- 修复建议：复用条件加 `src_mtime` 或内容 hash 比对；源图变则重做超分。

### 1.3 compose 时序门禁用"持久化时长"，合成却"重算时长" — `compose.py:219` vs `:240`
```python
if run_timing_gate and ep.shots:
    assert_timing_or_raise(ep)          # ① 校验持久化 shot.duration_ms
...
for sh in shots:
    a_dur = f.audio_duration_ms or 0
    sh.duration_ms = sh.audio_start_ms + a_dur + tail_of[sh.id]   # ② 用 frame.audio 重算
```
①对**episode.json 里存的** shot 时长断言（内部自洽）；②合成时用 **frame.audio_duration_ms 重算**。若某 frame 漏合成（`audio_duration_ms=None/0`），①通过（它比的是持久化值），②却重算出 ~250ms 的闪镜，**绕过门禁静默出闪镜/空镜**。
- 同理：无断言校验 `frame.audio_duration_ms` 与**磁盘 wav 实际时长**一致。若 wav 被覆盖/损坏但 json 没更新，门禁不拦。
- 修复建议：门禁在重算**之后**跑一次，或用真实 wav 时长回填 frame 后再 gate。

## 2. P1 高危（可能出错/中断留半成品/移植风险）

### 2.1 compose 收口卡死无超时 — `compose.py:322,377`
`proc.wait()` **无 timeout**，且 stderr 在 wait 之后才读（:380）。ffmpeg 出错 stderr 填满管道缓冲 → ffmpeg 写阻塞 → wait 永不返回 → **主进程永久卡死**（只读审计中无法复现，但这是标准 Popen 死锁模式）。
- **无 `.tmp` 原子改名**：`final = out_dir/{id}_m1.mp4` 直接写真名，中断/卡死 → **半成品 mp4 以真名留下**，覆盖好片（本项目 m1_compose 时代曾反复踩）。
- 修复建议：`proc.wait(timeout=N)` + 超时 kill；写 `.tmp` 收口后 `os.replace` 成真名（与 upscale.py 已加的原子写同款）。

### 2.2 孤儿 ffmpeg 残留 — `compose.py` 全程无 signal/atexit/try-finally
Windows 强杀主 python 不连带杀 ffmpeg → 孤儿 ffmpeg 继续写/占输出文件。本项目真实发生过（本次会话见孤儿 ffmpeg 占着 mp4、`.tmp` 壳卡死）。无清理机制。

### 2.3 跨 episode 复用底图走绝对路径 — `hanwu-ch3.json`/`hanwu-feature.json`
- `hanwu-ch3.json` 101 条 `image_path` 全以 `D:/hv/` 开头，其中 64 条指向 `episodes/hw-002/shots/`（跨集复用 SC01/02/03/11/13/19/20/23/24）。
- `hanwu-feature.json` 53 条，17 条指向 hw-002。
- **换盘符/换机即全失效**；`grep 'D:/hv' app/ bin/` = 45 处硬编码路径。当前数据未缺失（抽查 image/audio 全存在），纯移植性 P1。

### 2.4 时序 gate 是可传参绕过的软门禁 — `compose.py:194,218`
`run_timing_gate` 默认 True，任何调用方传 False 即跳过 → 短镜能悄悄出片（2026-09-03 审计 #A 根因）。无编译期强制。当前无活跃绕过路径，但缺"不可关"护栏。

### 2.5 编码漂移（部分已修，残留 motion） 
- ✅ **compose.py 已修复**（Task #31）：`:297-309` 读 `config.compose`，NVENC High/4.1 生效（本会话三章全 High/4.1 验证）。
- ⚠️ **残留**：`motion.py:266` 的 `motion.render()`（每镜预览 mp4）仍硬编码 `libx264 -crf`，且 compose.py:14 注释称"由 motion.render() 单独生成"——但当前 episodes 的 shots/ 下 **0 个预览 mp4**（未被实际调用）。doc/代码双漂移。

### 2.6 cosyvoice 双实现并存 — `app/services/cosyvoice.py`
`:95` `CosyVoice2Synthesizer`（本地 V-API 中转）与 `:351` `DashScopeCosyVoiceSynthesizer`（云端）双实现；生产路径 `voice.py:111` 只走云端 `synthesize_dashscope_whole`。本地版疑似死实现。架构之争物理残留。

- 回归：direct ffmpeg 验证 `-f mp4` 写 .tmp 成功 / 不带则失败；真实 hanwu-feature / prologue
